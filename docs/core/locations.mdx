A location is a named pin over a source-relative path. It helps a person return
to an important part of a source and can request stronger attention for that
subtree.

A location does not own records, trigger a separate index, or create another
file identity namespace.

## The three boundaries

Spacedrive separates capture, attention, and display:

| Boundary | Object | Question |
| --- | --- | --- |
| Capture | Source | What data do we retain from this origin? |
| Attention | Location | Which retained subtree needs a name or stronger policy? |
| Display | Lens | Which records should this view show? |

Combining these jobs causes duplicate indexes and confusing controls. A user
should not have to “add a location” merely to make a folder searchable if its
source already captures it.

## Location shape

A location stores only the identity and presentation needed for a pin:

- stable ID and UUID;
- source UUID;
- source-relative path;
- display name;
- origin label;
- creation time.

The source owns records and content evidence. The lens owns sorting and
filtering. File bytes remain at the origin.

## Default locations

A new library creates pins for common folders:

- Home
- Desktop
- Documents
- Downloads
- Pictures

These pins appear when their paths can resolve inside an attached source. They
do not start five overlapping scans.

## Retention and attention

Locations can ask a source to retain or process a subtree more strongly than
the source baseline. Examples include:

- keep this subtree available offline;
- identify content promptly;
- generate previews for supported file kinds;
- protect a minimum number of verified copies;
- watch this path while the rest of the source is scanned periodically.

The effective policy is a union. If several locations overlap, the strongest
requirement wins for the shared records. Removing one location removes only its
contribution.

For example, a Documents pin can request continuous watching while a Photos pin
requests previews and two verified copies. Records covered by both receive the
union of those requirements.

Policy never creates a second record for the same source object.

## Nested sources

A path can sit inside more than one configured source. The most specific source
owns capture for that path. Pins resolve against the selected source and its
relative path.

The underlying mounted filesystem still uses one arena identity namespace, so
nested sources do not make ordinary browsing unstable.

## Deleting a location

Deleting a location removes:

- the sidebar pin;
- its display name;
- its requested attention policy.

It does not remove source records, delete files, or erase content identities.
If the location supplied the last retention requirement for cached bytes, the
normal policy engine may later reclaim that cache. The origin remains
untouched.

## Moving or renaming a pin

Renaming changes only the label. Moving a location changes its source-relative
target after the destination has been resolved. Neither operation moves the
underlying directory.

Use a file move operation when you intend to change bytes or paths at the
origin.

## Locations in the interface

Locations are shortcuts, not the top-level storage model. Sources show where
data comes from and whether it is available. Locations surface the paths a
person uses often. Lenses and extensions add higher-level views such as Photos,
Duplicates, Screenshots, or project-specific dashboards.

This keeps the main interface simple:

- **Sources** explain custody and availability.
- **Locations** provide familiar entry points.
- **Views** explain what the user is trying to do.

## For extension authors

An extension may suggest or create a location when it needs a stable user-facing
entry point into an existing source. It should create its own view when the
concept is a query, workflow, or content type.

An extension must not treat a location as a private database boundary. Durable
extension assertions attach to stable source, record, or content identity.
