A location is a named pin over a source-relative path. It helps a person return
to an important part of a source and gives future policies a stable target.

A location does not own records, trigger indexing, enable a watcher, or create
another file identity namespace.

## The three boundaries

Spacedrive separates capture, navigation, and display:

| Boundary | Object | Question |
| --- | --- | --- |
| Capture | Source | What data do we retain from this origin? |
| Navigation | Location | Which source-relative path did the user pin? |
| Display | Lens | Which records should this view show? |

Combining these jobs causes duplicate indexes and confusing controls. A user
should not have to “add a location” merely to make a folder searchable if its
source already captures it.

## Location shape

A location stores only the identity and presentation needed for a pin:

- stable ID and UUID;
- source UUID;
- source-relative path;
- display name;
- origin label;
- creation time.

The source owns records, content evidence, and live freshness. The lens owns
sorting and filtering. File bytes remain at the origin.

## Places and known folders

Clients compute common navigation destinations when those folders exist on the
current device:

- Home
- Desktop
- Documents
- Downloads
- Pictures

These destinations appear under Places without creating location rows. A user
can remove or reorder them through presentation preferences without changing
the source model. Explicitly pinning another folder creates a location.

## Policy attachment

The current location row carries no indexing or retention policy. A filesystem
source captures its full configured root and watches that root after a
successful walk. Pinning and unpinning do not change either behavior.

Future features may attach explicit policies to a location ID, such as keeping
bytes offline or requiring verified copies. Those policies must be visible,
independently removable, and evaluated by the source. The existence of a pin
must never silently imply them.

An explicit policy still cannot create a second record for the same source
object.

## Nested sources

A path can sit inside more than one configured source. The most specific source
owns capture for that path. Pins resolve against the selected source and its
relative path.

The underlying mounted filesystem still uses one arena identity namespace, so
nested sources do not make ordinary browsing unstable.

## Deleting a location

Deleting a location removes:

- the sidebar pin;
- its display name.

It does not remove source records, delete files, or erase content identities.
It does not stop the source watcher or discard the source store. The origin
remains untouched.

## Moving or renaming a pin

Renaming changes only the label. A location target is not editable. Unpin the
old path and pin the new one if the shortcut should point somewhere else.
Neither operation moves the underlying directory.

Use a file move operation when you intend to change bytes or paths at the
origin.

## Locations in the interface

Locations are shortcuts, not the top-level storage model. Sources show where
data comes from and whether it is available. Locations surface the paths a
person uses often. Lenses and extensions add higher-level views such as Photos,
Duplicates, Screenshots, or project-specific dashboards.

This keeps the main interface simple:

- **Sources** explain custody and availability.
- **Places** provide familiar entry points, including locations and computed
  system folders.
- **Views** explain what the user is trying to do.

### Path status

The control beside the Explorer path bar explains the current path instead of
claiming that a location is indexed. It reports independent facts:

- the innermost source retaining the path;
- the mounted volume containing it, when one is known;
- whether metadata is only in memory, in a machine-local restart cache, or in
  a source store;
- whether a watcher currently covers the path;
- whether the volume map is unseen, indexing, detailed, or summarised;
- whether the path is a computed Place, an exact pin, or inside a pin;
- availability and permission failures.

The daemon resolves these facts through `paths.context`. Clients must not infer
them from path string prefixes or from the existence of a location row. On
macOS, the query resolves APFS data-volume aliases before matching sources and
pins.

From this control, **Add to Places** creates a location only when the path is
already inside a source. **Add to Spacedrive** opens source setup when no source
owns the path. Removing a pin changes navigation only.

## For extension authors

An extension may suggest or create a location when it needs a stable user-facing
entry point into an existing source. It should create its own view when the
concept is a query, workflow, or content type.

An extension must not treat a location as a private database boundary. Durable
extension assertions attach to stable source, record, or content identity.
