Spacedrive answers two kinds of question about what files say:

- `search.grep` reads files as they are on disk. It takes a regular
  expression, needs no index and is never stale, but its cost grows with the
  size of the tree.
- `search.content` answers a word query from an index. It returns ranked
  files with a snippet in milliseconds whatever the size of the tree, but it
  matches words rather than patterns and knows only what the last pass read.

Use `search.content` to find which files are about something, then
`search.grep` to find every line that matches a pattern in them. To find
files by what they mean rather than the words they use, see
[Semantic Search](/docs/core/semantic-search).

## What is indexed

Each source keeps its text index on the device that owns the source. The
index covers files with these extensions:

| Kind | Extensions |
|---|---|
| `text` | txt, text, log, rst, adoc, org, tex |
| `markdown` | md, markdown, mdx |
| `csv` | csv, tsv |
| `json` | json, jsonl, ndjson, geojson |
| `code` | rs, ts, tsx, js, py, go, swift, c, cpp, java, sh, sql, html, css, yaml, toml and other source and config formats |
| `pdf` | pdf |
| `docx` | docx |

Text formats are read as UTF-8. A file with a NUL byte is treated as binary
and skipped. PDF and DOCX files are parsed for their text. Files over 64 MiB are
not parsed, and neither is a PDF whose compressed streams expand past 256 MiB.
A file contributes at most the start of its text: 1,048,576 bytes for prose,
PDF and DOCX, 262,144 bytes for `code`, and 65,536 bytes for `csv`, `json`
and `.log` files. A hit on a file that held more is marked `truncated`, and a
word that only appears after the cap is not found. Lockfiles
(`package-lock.json`, `npm-shrinkwrap.json`, `pnpm-lock.yaml`) and files with
`.min.` in their name are not read.

Only files in the source's deep scope are read, and never a file in a hidden
folder or a hidden file. The deep scope is the set of folders where a source
reads file contents: the spaces with content indexing on, plus the source's
default. The home source's default is its OS user folders (Desktop, Documents,
Downloads, Pictures, Movies or Videos, Music, Public), which become spaces
when the source is tracked or its library opens, so a person turns them on and off like
any other space. Any other source reads its whole root. `spaces.create` with
content indexing on adds a folder, and `spaces.update` turns a space's content
indexing on or off. Content identification follows the same set.

The index never opens a cloud placeholder whose contents are not on the
device, because opening one downloads it. The file is indexed once its
contents are local. Symbolic links are not followed.

Words spoken in audio and video files are indexed too, once the files are
transcribed. See [Spoken words](#spoken-words). So are the descriptions
extensions write of what video shots and photos show. See
[Descriptions](#descriptions).

A source tracked without content identification reads no file contents, so it
has no text index. `search.content` refuses it and points to
`search.grep`. OCR and semantic search are not part of this index.

## How the index stays current

The index lives in `text.db`, next to the source store's `data.db`. It is
part of the store's generation half: every row comes from bytes the origin
still holds, so it never holds anything a person asserted and dropping it
loses nothing. It is a separate file so that writing large text never holds
the record store's write lock, and so a replica of the record store does not
carry it. An index written by a build that read every file is cleared and
vacuumed the first time it opens, and the next pass reads the deep scope
again. A pass that leaves free pages worth a quarter of the file, and at
least 16 MiB, merges the index and vacuums it.

A background pass fills it. The pass runs after each content identification
pass, which follows every walk, watcher change and returning volume. When a
watcher change, a reconcile or a returning volume leaves nothing to identify,
such as a rename, the text pass is queued on its own. It runs at background priority, on
the same low-priority threads as hashing.

Each row is keyed by the file's record and stamped with the size, modified time
and extension the record had when the text was read:

- **Create.** A new record has no row, so the next pass reads it.
- **Modify.** The record's size or modified time no longer matches the stamp,
  so the next pass reads it again. Until then the file is left out of results
  rather than answering with text it no longer holds.
- **Rename.** The record keeps its identity, so nothing is read again. Hits
  show the new path because paths come from the record store at query time. A
  rename to another extension reads the file again, since another extractor
  may apply, and a rename to an extension the index does not read takes the
  file out of results at once.
- **Delete.** The record is gone, so no search can reach its row. The next pass
  removes the row.

Each response carries `pending_files`, the number of files under the scope
whose text is missing or out of date. Zero means the index matches the record
store there.

## Query

```json
{
  "scope": { "Physical": { "device_slug": "local", "path": "/Users/me/notes" } },
  "query": "\"quarterly report\" budget",
  "kinds": ["markdown", "pdf"],
  "max_results": 20
}
```

- `scope` is a directory or file under a source tracked on this device.
- `query` matches whole words, and every word must appear. Text in double
  quotes is a phrase, and a word ending in `*` matches as a prefix. No other
  syntax is interpreted.
- `kinds` limits hits to files read by those extractors.
- `max_results` defaults to 20 and is at most 200. Pass a response's
  `next_cursor` back as `cursor` for the next page.

Each hit has a `path` relative to the scope, its `kind`, a BM25 `score`
(larger is better), and a `snippet` as a list of fragments, each marked
`matched` or not. A `transcript` hit also has a `time` with `start_seconds`
and `end_seconds`: the stretch of the recording where the words were said.
A `scene` hit has one too: the shot's in and out points.

From the CLI:

```bash
sd-cli search content 'quarterly report' ~/Documents --kind pdf --kind docx
sd-cli search content 'tokio::spawn' ~/Code/project --kind code
```

## From an agent

A folder lent through an [agent grant](/docs/cli/agent-access) exposes this
search as the `search_content` MCP tool. It takes the same query, kinds and
cursor, searches only inside the granted folder, and returns paths relative to
it. Hits whose file has moved out of the folder since the last pass are
dropped. The folder must sit inside a source tracked on the daemon's device
with content identification, otherwise the tool refuses and points to `grep`.

## Spoken words

The `media.transcribe` action transcribes audio and video files and adds what
was said to this index. It runs only in a daemon built with the
`speech-to-text` cargo feature. A default build leaves it off; the desktop
app's daemon is built with it. See [Transcription](./transcription).

Each transcript segment is a row of its own, so a hit names the moment, not
only the file. A recording that says the words in three places answers with
three hits, each with its `time`. Filter to spoken words with the
`transcript` kind:

```bash
sd-cli search content '"lighthouse was built"' ~/Footage --kind transcript
clips/talk.mp4 @ 0:14  (0.77)
    The [lighthouse was built] in 1902 by the Harbour Master.
```

The words of one hit must sit in one segment. Whisper ends a segment at a
sentence or a pause, so a phrase that runs across one is not found as a
phrase; search for its words without quotes.

Transcript rows follow the record like the other rows: an edited recording
drops out of results until it is transcribed again, and a renamed one keeps
its transcript. The ranks of a segment and a whole document are on the same
scale, but a segment is short, so it tends to rank above a long document
that holds the same words.

## Descriptions

Extensions describe what content shows in sidecars, and this index holds
their text so a word query finds a file by what is in it:

| Kind | Sidecar | Written by | Indexed in a build with |
|---|---|---|---|
| `scene` | `scene`, one description per shot keyframe | Videos extension | `video-shots` |
| `caption` | `caption`, one description per photo | Photos extension | `ai-cloud` |

Both cargo features are off in a default build, and the host runs extensions
only in a build with `wasm`. The desktop app's daemon is built with all three
through the `footage` feature. The index is updated when the extension writes, replaces
or deletes the sidecar.

Each described shot is a row of its own, timed from the video's shot list, so
a `scene` hit names the shot with its `time`. A shot the list no longer names
is still found, without a `time`. A `caption` hit has no `time`.

```bash
sd-cli search content lighthouse ~/Footage --kind scene
day1/harbour.mp4 @ 0:04  (1.32)
    A red [lighthouse] on a rocky point
```

Sidecars are keyed by the bytes, not the file, so every copy of a file
answers, and a description lands in every source on this device that holds
those bytes when the sidecar is written. A source that gains a copy later is
not filled in until the extension writes the sidecar again. The rows are
replaced only by sidecar writes, so a rebuild keeps them.

## Rebuild

`search.content.rebuild` drops a source's index and starts a pass that reads
every file again. The record store is not touched. Transcripts and
descriptions are kept, since the text pass cannot make them again;
`media.transcribe` with `force` redoes transcripts.

```bash
sd-cli search reindex-content ~/Documents
```

A rebuild that lands while a pass is running restarts that pass from the
first file. The pass is refused while the source's volume is away, so the index stays
empty until the volume returns. Searching a source owned by another device is
not available yet; run the search on that device.
