Tags are user assertions. They are not filesystem metadata and cannot be
recreated by scanning an origin, so they live in the durable assertion layer.

## Tag identity

A tag has a stable UUID, display name, optional color, and library scope.
Renaming a tag changes its label without rewriting every attachment.

Tag names are not global identity. Two libraries can use the same name for
different concepts.

## Attachment scope

A tag can attach to:

- a source record, when it describes one observed instance;
- confirmed content, when it should follow identical bytes across sources;
- a standalone extension model, when it describes a domain object.

The scope is explicit. Spacedrive does not silently move a record tag to every
candidate duplicate.

## Why content confirmation matters

A sampled hash creates candidate content identity. It is useful for finding
likely duplicates but is not strong enough to merge durable user organization.

Attaching a tag to content requires confirmed identity or explicit approval.
Record-scoped tags remain safe even before hashing.

## Reindexing

Record overlays survive source generation replacement. When a fresh ingest sees
the same stable object, its tags remain attached. When identity cannot be
proven, the old assertion is preserved as unresolved rather than reassigned to
a similar path.

Paths are hints, not attachment keys.

## Sync

Authorized devices can edit tags while offline. Each attachment records
provenance and logical time.

Independent adds merge. A remove records intent against the observed
attachment, so a delayed packet does not blindly erase a later add. Permission
changes can require explicit confirmation instead of ordinary merge.

Filesystem modification time never orders tag changes.

## Search and views

Tag queries join through stable source, record, or content identity. Results
report source availability and can include offline records.

Views can combine tags with file kind, path, dates, people, or extension fields.
The tag system remains a small organization primitive rather than becoming a
separate file tree.

## Permissions

Grants can restrict:

- reading tag names;
- seeing attachments;
- creating or renaming tags;
- attaching tags to a source scope;
- removing another actor's assertion.

An extension or agent receives the same checks as a graphical client.

## Deletion

Deleting a tag previews the number and scopes of affected attachments. It never
deletes file bytes.

For audit-sensitive libraries, deletion can tombstone the tag while preserving
provenance and historical views.

## Extension use

Extensions should use tags for user-facing labels and lightweight
classification. Rich domain facts belong in typed extension models.

A Photos extension may expose a person name as a view backed by a person model,
then let a user add ordinary tags such as Favorites or Print. It should not
encode an entire face graph into tag strings.

## Core rules

- Tags are assertions, not generated source data.
- Stable IDs outlive names and paths.
- Record and content attachments are distinct.
- Candidate hashes do not merge durable organization.
- Reindexing preserves assertions.
- Sync carries provenance and explicit remove intent.
- Tag deletion never implies file deletion.
